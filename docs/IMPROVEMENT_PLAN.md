### 1. 可选集成青龙服务端至 App（探索项）

用户提出参考 [SimonSchubert/Kai](https://github.com/SimonSchubert/Kai) 的 Android Sandbox。
需要先校正参考事实：Kai 当前 README 描述的是**无 Root 的 Alpine Linux + proot 沙箱**，并非已确认的
Debian 方案；它通过应用内安装轻量用户空间、可选 bash/curl/git/python/Node 等包并提供终端执行。
因此本项目只能把它作为“Android 内 Linux 用户空间”的可行性参考，不能把 Debian/Alpine、proot
和青龙运行时依赖当作已经验证的技术选型。

- [ ] 先做外部伴随模式 PoC：由用户自行安装 Termux/兼容 Linux 沙箱和青龙，AzureQL 仅负责检测
  `127.0.0.1:5700`、健康检查、账户绑定和远程/本机连接切换；不承诺后台保活。
- [ ] 再评估 App 私有目录内的可选沙箱：rootfs、proot/解释器、Node/Python 原生依赖、定时器、
  日志、升级回滚和进程回收必须隔离为独立 `LocalQingLongRuntime`，不得侵入现有远程
  `ApiClientRegistry`/Session 逻辑。用户必须显式安装、启动、停止和删除，默认不占用 APK 与存储空间。
- [ ] 本地服务只绑定 loopback，并复用现有认证边界；Token、脚本、变量和备份不得因为本地模式绕过
  TLS/证书校验、Agent Scope、审计或二次确认。
- [ ] 运行期间需要前台服务、通知、低内存回收和厂商省电策略说明；每条命令必须串行、有超时、可取消，
  提供沙箱重启/故障恢复入口并清理孤儿进程。
- [ ] 验收：冷启动、安装/升级/卸载、网络隔离、脚本/依赖/变量/备份、进程重建、后台限制、低存储、
  断电恢复和账户删除清理；本机模式失败时可无损切回远程服务端。

已知风险：Kai 的公开 [Sandbox degradation issue #359](https://github.com/SimonSchubert/Kai/issues/359)
报告过 proot 长时间运行变慢、并行命令争用和应用卸载后残留进程；这不是本项目结论，但说明必须把
命令串行、看门狗、重启和卸载清理列为 PoC 的验收项。完整 APK 内嵌青龙仍按既有评估估算为高风险、
高维护成本方案，当前不建议直接承诺为正式功能。

### 4. WebDAV 备份目标

目标是“通过青龙备份 API 生成归档，再保存到用户指定的 WebDAV 目录”，不是把青龙 Token 交给 WebDAV
服务端，也不是默认上传到第三方云盘。接口字段先以当前青龙实例为准，[ql-api-swagger](https://github.com/Eikeitsu/ql-api-swagger)
仅作为交叉核对来源；实现前必须用真实青龙版本确认导出响应和兼容性。

- [ ] 设置中增加按账户隔离的 WebDAV 配置：服务器 URL、远程目录、文件名模板、用户名/应用密码，
  可选自签名证书信任配置；凭据使用 Android Keystore 加密，不进入 Room、日志、URI 或备份归档。
- [ ] 导出流程调用现有青龙 `api/system/data/export` 能力并流式转发到 WebDAV `PUT`；不把整份归档
  读入内存。优先上传到 `.part` 临时名，完成后通过 WebDAV MOVE/重命名为最终文件；不支持 MOVE 时
  使用唯一时间戳文件名并通过 HEAD/长度/哈希确认完整性。
- [ ] 保留现有五阶段进度、取消、WorkManager/前台通知和错误分类；WebDAV 认证失败、TLS 失败、
  目录不存在、空间不足、超时、断网、冲突和服务端导出失败必须分别提示。失败或取消清理 `.part`，
  重试不得重复生成不可识别的半成品。
- [ ] 明确覆盖策略（拒绝、询问、版本化文件名），支持按账户/日期分目录；默认不覆盖已有归档。
  是否支持从 WebDAV 下载并恢复另列为后续需求，不能把“上传成功”当成“恢复可用”。
- [ ] 验收：MockWebServer/WebDAV 兼容服务与真实 WebDAV 各覆盖小/大归档、401/403、409、404、507、
  TLS/证书、限速、断网/恢复、取消、进程重建、重复文件和磁盘不足；校验服务端归档可解压且与青龙
  导出内容一致，并确认 Token/密码不出现在网络日志或本地明文。

四项的建议顺序为：先完成设置内多账户管理，再实现内置编辑器；WebDAV 可复用备份流式传输后接入；
本机青龙服务端先做外部伴随 PoC，只有在沙箱生命周期、依赖和后台限制均有可接受证据后，才评估 App
私有目录内嵌方案。

### A. P0：修复设置里的服务器数据恢复

**当前现象**

- 选择备份文件并导入后失败，客户端显示：

  ```text

  JSON input: {"code":200,"data":"data/db/andata/.../database.sqlite..."}
  ```

- 导入过程缺少持续可见的进度圈或阶段提示，用户无法判断是否仍在上传、解析、
  激活数据或等待青龙服务重启。

**初步定位**

- 客户端当前把 `PUT /api/system/data/import` 声明为 `ApiResponse<Unit>`，而青龙成功
  响应的 `data` 实际可能是字符串形式的服务端文件路径。HTTP 与业务码均已成功，
  但客户端在反序列化 `$.data` 时把字符串误当成对象，因此在调用
  `PUT /api/update/data` 前就报错。

**目标与验收**

- [x] 导入接口兼容青龙当前返回的字符串 `data`，同时容忍未来无 `data` 或返回
  其他 JSON 值；只在 `code == 200` 后进入恢复确认，不能吞掉真正的服务端错误。
- [ ] 从用户确认导入开始，持续显示不可重复点击的忙碌状态；已知文件长度时显示
  上传百分比，未知长度时显示不确定进度圈。
- [ ] 明确展示“校验文件、上传备份、等待确认、激活数据、等待服务恢复”五个阶段；
  上传阶段允许取消，开始激活后不再显示会造成状态不确定的假取消。
- [ ] 分开提示 HTTP 错误、响应解析错误、备份格式错误、数据激活失败和健康检查超时，
  错误信息不得泄露 Token、密码或完整服务器内部路径。
- [ ] 使用包含上述字符串 `data` 的真实成功响应完成一次恢复；再覆盖无 `data`、
  非 200 业务码、HTTP 4xx/5xx、断网和服务重启超时测试。

### D. P0：修复依赖安装、重装和删除的响应/状态判定

**当前现象**

- 重新安装依赖时提示：

  ```text
  重新安装失败: Unexpected JSON token at offset 19:
  Expected start of the object, but had '[' instead at path: $.data
  JSON input: {"code":200,"data":[{"id":69,"name":"tesseract-ocr",...}]}
  ```

- 强制删除依赖时出现相同的 `$.data` 数组解析错误。
- 新安装依赖被界面标成“安装失败”，但日志只有类似以下的启动记录，没有成功或失败
  的结束记录：

  ```text
  开始安装依赖 tesseract-ocr，开始时间 2026-08-20 12:43:39
  ```

**已确认的接口行为与初步定位**

- 青龙的 `POST /api/dependencies`、`PUT /api/dependencies/reinstall` 和
  `DELETE /api/dependencies/force` 均可能在 `data` 中返回依赖对象数组。
- 客户端目前只把新增接口声明为 `ApiResponse<List<DependencyInfo>>`；重装与强制删除
  被错误声明为 `ApiResponse<Unit>`。因此 HTTP 和业务码已经成功、服务端任务也可能
  已经开始，但客户端在解析数组时误报失败。
- 青龙安装是异步任务：新增/重装接口成功只表示记录已创建并进入队列，不表示安装
  已完成。“开始安装依赖”也只是启动日志，不能单独作为成功或失败终态。
- 官方状态码为：`0 安装中`、`1 已安装`、`2 安装失败`、`3 删除中`、`4 已删除`、
  `5 删除失败`、`6 队列中`、`7 已取消`。当前卡片把队列中等非终态也使用错误色，
  容易造成“刚提交就失败”的误解。

**目标与验收**

- [x] 重装和强制删除接口按实际响应解析依赖对象数组；同时兼容合法的空 `data`，
  不能再用 `ApiResponse<Unit>` 强制反序列化数组。
- [x] HTTP/业务码成功后显示“任务已提交”或“队列中”，并优先把响应数组中的最新记录
  合并到本地列表；不能因为后续刷新暂时返回旧状态而立即改成失败。
- [ ] 通过依赖日志 WebSocket 和 `GET /api/dependencies/{id}` 跟踪异步状态；WebSocket
  中断时回退为有限频率轮询，离开页面或进入终态后停止监听。
- [x] 只有服务端明确返回状态 `2` 或 `5` 时才显示安装/删除失败；状态 `6` 使用中性
  “队列中”，状态 `0/3` 显示进度，状态 `1/4` 才显示完成。
- [ ] 日志仅有“开始安装”而没有终态时保持“安装中”，刷新日志和记录状态；若服务端
  已标记失败但缺少结束日志，提示“服务端标记失败，日志不完整”，不能伪造成功原因。
- [ ] 新增、重装和删除期间禁用同一依赖的重复操作；批量操作逐项展示已提交、执行中、
  成功、失败和取消数量，解析错误不得覆盖服务端真实执行结果。
- [x] 依赖名称和类型在卡片、确认框与日志标题中用空格或标签明确分隔，避免显示成
  `tesseract-ocrlinux` 这类容易误读的连续文本。
- [ ] 使用返回数组的新增、重装、普通删除和强制删除响应各完成测试；再覆盖排队→安装中
  →成功、排队→安装中→失败、删除失败、取消、WebSocket 断线和日志不完整场景。
- [ ] 在测试青龙实例新增 Linux 依赖 `tesseract-ocr`，确认初始只显示已提交/队列中，
  最终状态严格以青龙返回值和完整结束日志为准。

### F. P2：服务端通知同步到 Android 本地通知（只评估，暂不实现）

**可行性结论**

- 可以实现，但青龙服务端无法可靠地直接向一台普通 Android 手机发送 HTTP 回调。
  手机通常位于 NAT 后方，Android 也会限制后台常驻 HTTP 服务；把 `WEBHOOK_URL`
  指向手机局域网地址只在极少数前台、同网段场景工作，不能作为正式方案。
- 青龙当前没有“通知收件箱/历史列表”API，WorkManager 最短约 15 分钟的轮询既不实时，
  也无法完整补取通知，因此不推荐用客户端轮询伪装实时同步。
- 推荐方案是“青龙自定义 Webhook → 可从公网或指定网络访问的中继服务 → FCM →
  AzureQL 本地通知”。中继可以自托管，但属于新增服务端组件；本功能与
  `qinglong-cloudflare-worker` 无关，也不得复用该项目。

**必须先区分的两类通知**

1. 青龙自身的登录等系统通知使用 `GET/PUT /api/user/notification`，通知配置保存在
   青龙数据库。官方接口当前只保存一种 `type`，切换为 AzureQL Webhook 可能替换用户
   已有的 Telegram、Bark 等系统通知渠道。
2. 定时脚本调用通知脚本时通常读取 `config.sh` 中的 `WEBHOOK_*` 环境变量。这与上面的
   用户通知配置不是同一套数据；只调用 `/api/user/notification` 不会自动改写
   `config.sh`。

**推荐架构（待用户确认）**

- [ ] 设置中提供每个服务器/账户独立的“同步服务端通知”开关；开启时才解释用途并请求
  Android 13+ 的 `POST_NOTIFICATIONS`，拒绝权限不影响其他功能。
- [ ] AzureQL 向中继注册 FCM Token、服务器标识和随机生成的高强度接收凭证；中继只
  接收 HTTPS，不保存青龙登录 Token、密码或脚本环境变量。
- [ ] 青龙 Webhook 使用 `POST application/json`，Body 至少包含 `$title` 和
  `$content`；鉴权密钥放在 Header，不放在通知正文。中继进行限流、长度限制、重复
  消息抑制和凭证撤销。
- [ ] 本地通知按服务器建立 Channel，支持隐藏锁屏正文、点击进入对应账户、单独静音和
  关闭；切换账户或注销时注销相应接收凭证。
- [ ] 若用户已有青龙系统通知渠道，启用前必须提示“官方接口只允许一个渠道”；在没有
  中继转发能力前不得静默覆盖旧配置。

**`config.sh` 注入方案（仅在需要同步脚本通知时启用）**

- 青龙允许通过 `GET /api/configs/detail?path=config.sh` 读取全文，并通过
  `POST /api/configs/save` 保存全文。该接口不是字段级更新，直接覆盖存在并发修改和
  破坏用户自定义内容的风险。
- [ ] 不使用宽泛正则替换整个“自定义通知”章节。客户端只维护带有明确开始/结束标记的
  AzureQL 区块；首次注入前保存原文和内容哈希，显示差异预览并要求用户确认。
- [ ] 保存前重新读取并比较哈希；发现用户或其他程序已修改 `config.sh` 时停止并要求
  合并，不能用旧副本覆盖。
- [ ] Shell 值必须正确转义，`$title`/`$content` 保持为通知脚本运行时占位符。推荐的
  托管区块形态如下，实际地址和凭证必须由已敲定的中继方案生成：

  ```sh
  # >>> AzureQL managed notification >>>
  export WEBHOOK_URL="https://<relay-host>/v1/qinglong/notify"
  export WEBHOOK_BODY='{"title":"$title","content":"$content"}'
  export WEBHOOK_HEADERS=$'Authorization: Bearer <receiver-secret>\nX-AzureQL-Server: <server-id>'
  export WEBHOOK_METHOD="POST"
  export WEBHOOK_CONTENT_TYPE="application/json"
  # <<< AzureQL managed notification <<<
  ```

- `IPPORT='http://qinglong:5700'` 是容器内部访问地址，不是手机或推送中继的回调地址；
  AzureQL 不应自动新增、修改或依赖该变量，除非另一个脚本功能明确需要它。
- [ ] 关闭同步时只删除 AzureQL 自己的托管区块并注销中继凭证，不删除用户手写的
  `WEBHOOK_*` 或其他通知渠道；提供恢复原配置入口。

**实施前必须敲定的决策**

- [ ] 是否接受部署一个可达的自托管中继并使用 FCM；若不接受，只能选择“应用在线时
  接收”或“延迟且不完整的轮询”，不能承诺可靠实时通知。
- [ ] 同步范围是仅青龙系统通知、仅脚本通知，还是两者都要。
- [ ] 若 `/api/user/notification` 已配置其他提供商，是禁止覆盖、让中继同时转发旧渠道，
  还是由用户明确选择替换。
- [ ] 锁屏通知默认显示完整正文、仅标题，还是完全隐藏敏感内容。
- [ ] 中继的部署位置、数据保留期限、凭证轮换与删除策略必须形成单独的威胁模型和验收
  标准后，才能开始 Android 与服务端实现。

### Android 本机运行青龙服务端可行性评估

**结论：标准 Android 12+ 应用中完整内置官方青龙服务端技术上可以尝试，但不适合作为
AzureQL 的正式功能；推荐保留远程服务端，并只考虑“外部 Termux/用户自管本地服务端”实验模式。**

- [x] 青龙原生部署依赖 Linux 用户空间以及 Node.js、npm、pnpm、Python、pip、Shell、Git、
  定时与进程管理；Docker/Alpine 方案还依赖 `crond`，并非一个可直接放进 APK 的 Java 库。
- [x] AzureQL 目标 SDK 37；Android 10 起禁止普通应用直接执行写入其数据目录的可执行文件。
  即使把基础解释器预编译进 APK，后续下载的原生 Node/Python 依赖仍存在 ABI、动态加载、
  SELinux 与 W^X 兼容问题。
- [x] 持续运行还需要前台服务和常驻通知，并受到 Android 12+ 后台启动限制、厂商省电策略、
  用户强制停止以及低内存回收影响，无法承诺与 Linux/Docker 服务端相同的可用性。
- [x] Android Virtualization Framework 目前仅覆盖部分 ARM64 设备，创建或管理 pVM 需要平台
  签名权限；不能作为普通 GitHub/应用商店 APK 的通用方案。

**工作量预估**

- [ ] Termux 外部伴随模式 PoC：约 2～4 人周。由用户安装 Termux/青龙，AzureQL 负责引导、
  检测 `127.0.0.1:5700`、健康检查和切换连接；不承诺后台保活。
- [ ] 可公开测试的 Termux 伴随模式：约 6～10 人周，另需持续适配 Android/OEM、青龙版本、
  ARM64 包、升级回滚、日志、存储与权限问题。
- [ ] AzureQL APK 内完整嵌入运行时：至少 3～6 人月，并会显著增加 APK/数据占用和长期维护；
  仍难兼容任意 Linux、Node 原生模块与 Python 原生依赖，当前不建议立项。
- [ ] Root/chroot/第三方容器集成：约 2～4 人周可做实验，但只适合高级用户，不作为默认方案。

### A. Macrobenchmark、Baseline Profile 与回归门槛

第一批 Macrobenchmark 场景固定为：

1. 冷启动：分别测量 TTID（Time To Initial Display）和 TTFD（Time To Full Display）。
2. 首页 → 任务 → 环境变量 → 依赖 → 脚本，连续切换底部 Tab。
3. 500/1000 项任务列表连续滚动，使用 `FrameTimingMetric` 测量帧耗时。
4. 展开大型脚本目录并连续滚动。
5. 分别打开 1 MiB、5 MiB、20 MiB 日志。
6. 分别打开并翻阅 10 MiB、50 MiB 脚本。
7. 打开订阅日志并保持 60 秒轮询。

Baseline Profile 覆盖启动、导航和滚动关键路径，但测试结果必须拆成两组，避免其掩盖代码优化效果：

- **架构优化对比**：旧代码与新代码使用完全相同的 `CompilationMode`。
- **最终生产性能**：分别测量 Baseline Profile OFF 与 ON。

最终报告应能区分初始化缩减、Session/客户端复用和 Baseline Profile 各自带来的收益，不能只给出
混合后的总百分比。

将以下指标作为性能 regression gate（回归门槛）：

```text
Retrofit builds / 60 requests <= 1
SSLContext builds / 60 requests <= 1
Keystore decryptions / cached+refresh <= 1 initialization round
max rendered log window <= 256 KiB
main-thread file hashing = 0
search requests during 10 rapid keystrokes <= 1~2
MCP service shutdown main-thread blocking = 0 ms
```

### B. ApiClientRegistry 与连接配置生命周期

Retrofit/mTLS 优化不能只缓存一次 `Provider.get()` 的返回值，应建立由连接配置决定生命周期的
客户端注册表：

```text
ApiClientRegistry
├── ConnectionProfileKey
│   ├── baseUrl
│   ├── clientCertFingerprint
│   ├── caFingerprint
│   ├── tlsPolicy
│   └── networkPolicyVersion
│
└── CachedClient
    ├── OkHttpClient
    ├── Retrofit
    └── AutoPanelApiService
```

实现边界：

- Access Token 不得进入 `ConnectionProfileKey`。Token 刷新不能导致 Retrofit、OkHttp 或
  SSLContext 重建。
- 认证拦截器应从内存 `SessionSnapshot` 读取当前 Token。
- 相同 `ConnectionProfileKey` 的并发创建必须由 `Mutex` 或等价机制保护，避免两个请求同时
  构造相同客户端。
- 切换或删除配置时只失效对应连接，不清空无关账户的客户端。

客户端与 Session 失效矩阵：

| 事件 | Retrofit/OkHttp | Session |
|---|---:|---:|
| Token 更新 | 不重建 | 更新 |
| 登录/重新认证 | 通常不重建 | 更新 |
| 切换 Host | 重建/切换到对应缓存 | 切换 |
| 更换客户端证书 | 重建 | 保留或重新认证 |
| 更换 CA | 重建 | 保留 |
| 开关 mTLS | 重建 | 保留 |
| 删除账户 | 移除对应缓存 | 清除 |

同一连接配置生命周期的验收指标：

```text
Retrofit build count <= 1
OkHttp build count <= 1
SSLContext build count <= 1
client certificate load count <= 1
CA load count <= 1
```

### B.1 SessionSnapshot 与凭据单次初始化

Session 优化必须与客户端注册表在同一批完成，因为它们处于同一条请求链。建议的内存快照边界：

```kotlin
data class SessionSnapshot(
    val accountId: Long,
    val baseUrl: String,
    val token: String?,
    val username: String?,
    val clientId: String?,
    val clientSecret: String?,
    val tlsProfile: TlsProfile,
)
```

当前应消除的请求链：

```text
Repository
  -> Provider.get()
  -> getSession()
  -> DataStore
  -> Keystore
  -> AES-GCM decrypt
  -> Retrofit.Builder
  -> SSLContext
  -> request
```

目标请求链：

```text
Repository
  -> ApiClientRegistry
  -> existing AutoPanelApiService
  -> AuthInterceptor
  -> in-memory SessionSnapshot
  -> request
```

`SessionManager` 只在以下事件重新加载或更新：

- App 首次真正需要当前账户。
- 账户切换。
- 登录成功或重新认证。
- Token 更新。
- 证书配置改变。
- 账户编辑。
- 账户删除。

不得在每次 API 或缓存操作中重新调用持久化 `getSession()`。首页一次缓存读取加刷新目前可能触发
约 6 次 `getSession()` 和最多约 24 次 AES-GCM 解密；优化后目标为：

```text
首次进入：1 次 DataStore 读取 + 1 轮必要凭据解密
后续请求：0 次 DataStore + 0 次 Keystore + 0 次 AES-GCM
```

### C. 服务端原始数据与本地化边界

来自青龙服务器的数据必须保持逐字节语义一致，展示层禁止翻译、rewrite 或 `replace`。AzureQL
自己生成的按钮、提示和状态文案仍可正常本地化。

以下内容必须原样显示、复制和传递：

- 任务日志、订阅日志。
- 脚本源码。
- `config.sh` 和其他配置文件。
- Shell、Python、Node 输出。
- 异常堆栈。
- 依赖安装输出。
- MCP 工具返回的日志与脚本内容。

该要求同时属于 **P0 correctness + performance**：修改 `Connection refused`、
`Module not found`、`error` 等服务器文本既会增加大文本扫描成本，也会破坏人类和 AI Agent
看到的数据完整性。

### C.1 Windowed Log Viewer

大日志不能仅由单个 `Text` 改成对完整内容执行 `split("\n")` 后交给 `LazyColumn`。这种方式仍会
为数十万行创建大量 `String`，产生明显内存和 GC 压力。

日志查看器应只持有有限窗口：

```text
LogViewer
├── currentWindow: 64–256 KiB
├── tailMode
├── offset
├── hasPrevious
├── hasNext
└── loadMore()
```

- 优先直接复用订阅日志接口已有的 `offset`、`limit`、`tail`；当前默认 `limit = 65536`
  可以直接作为 64 KiB 初始窗口。
- UI 任意时刻渲染的日志窗口不得超过 256 KiB。
- 向前/向后加载时替换或裁剪窗口，不在 Compose 状态中累计整个日志文件。
- Tail 模式只追加窗口范围内的新内容，并明确处理日志轮转、offset 失效和请求取消。

### P0/P1 交界：脚本 SHA-256 与文件大小分级

`serverChangedSinceDownload()` 在 size/mtime 无法判断时会下载正文并计算 SHA-256；流式哈希必须
明确进入 I/O 调度线程并支持协程取消：

```kotlin
withContext(Dispatchers.IO) {
    ensureActive()
    currentBody.sha256()
}
```

哈希循环也应周期性调用 `ensureActive()`，确保页面离开或新请求替代旧请求时能及时停止。

编辑能力按文件大小分级：

| 文件大小 | 默认能力 |
|---|---|
| `<= 5 MiB` | 普通编辑器 |
| `5–50 MiB` | 大文件编辑器，有限窗口/分页 |
| `> 50 MiB` | 只读或交给外部编辑器 |

不得仅依赖已有 50 MiB 总上限，也不得在主线程读取或哈希完整文件。
