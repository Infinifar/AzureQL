### A. P0：修复设置里的服务器数据恢复

**当前现象**

- 选择备份文件并导入后失败，客户端显示：

  ```text
  Unexpected JSON token at offset 19: Expected start of the object '{',
  but had '"' instead at path: $.data
  JSON input: {"code":200,"data":"data/db/andata/.../database.sqlite..."}
  ```

- 导入过程缺少持续可见的进度圈或阶段提示，用户无法判断是否仍在上传、解析、
  激活数据或等待青龙服务重启。

**初步定位**

- 客户端当前把 `PUT /api/system/data/import` 声明为 `ApiResponse<Unit>`，而青龙成功
  响应的 `data` 实际可能是字符串形式的服务端文件路径。HTTP 与业务码均已成功，
  但客户端在反序列化 `$.data` 时把字符串误当成对象，因此在调用
  `PUT /api/update/data` 前就报错。

**目标与验收**

- [x] 导入接口兼容青龙当前返回的字符串 `data`，同时容忍未来无 `data` 或返回
  其他 JSON 值；只在 `code == 200` 后进入恢复确认，不能吞掉真正的服务端错误。
- [ ] 从用户确认导入开始，持续显示不可重复点击的忙碌状态；已知文件长度时显示
  上传百分比，未知长度时显示不确定进度圈。
- [ ] 明确展示“校验文件、上传备份、等待确认、激活数据、等待服务恢复”五个阶段；
  上传阶段允许取消，开始激活后不再显示会造成状态不确定的假取消。
- [ ] 分开提示 HTTP 错误、响应解析错误、备份格式错误、数据激活失败和健康检查超时，
  错误信息不得泄露 Token、密码或完整服务器内部路径。
- [ ] 使用包含上述字符串 `data` 的真实成功响应完成一次恢复；再覆盖无 `data`、
  非 200 业务码、HTTP 4xx/5xx、断网和服务重启超时测试。

### B. P0：修复环境变量备份导入 HTTP 500，并补齐置顶

**当前现象**

- “环境变量 → 导入备份”会返回 HTTP 500。
- 官方 API 已提供 `PUT /api/envs/pin` 与 `PUT /api/envs/unpin`，但客户端仓库层、
  ViewModel 和界面尚未接通，所以环境变量没有置顶/取消置顶操作。

**目标与验收**

- [x] 导入前解析并校验本地备份，只向服务端发送 `name`、`value`、`remarks` 等
  官方新增/更新接口接受的字段，不回传旧记录的 ID、状态和时间戳。
- [ ] 导入前给出新增、重复、无效和总数量摘要；重复名称必须采用明确策略，不能让
  一条冲突导致整批以 HTTP 500 失败。部分失败时显示成功/失败数量和可重试项目。
- [x] 对较多变量分批提交，保留服务端返回的可读错误，但日志和提示不得输出变量值。
- [x] 兼容当前客户端导出的备份；损坏 JSON、空文件、缺少名称/值时在本地拦截，
  不发起网络请求。
- [x] 单个环境变量提供“置顶/取消置顶”操作；批量选择模式也提供对应操作。
- [x] 置顶成功后立即更新本地状态，刷新后仍由服务端顺序决定且置顶项排在前面；
  请求失败时恢复原状态并给出提示。
- [ ] 使用空备份、含重复名称的备份、100 条以上备份以及服务端部分失败场景验收，
  确认不再只显示笼统的 HTTP 500。

### C. P0：修复大脚本乱码/HTTP 400，并增加长按复制路径

**当前现象**

- 打开或保存较大脚本时偶发乱码或 HTTP 400。
- 脚本树虽然向条目传入了长按回调，但条目当前只使用普通 `clickable`，实际长按
  不会触发预期行为。

**目标与验收**

- [x] 分别记录并定位“获取内容”和“保存内容”的失败阶段，区分服务端 HTTP 400、
  网络超时、JSON 解码和文本渲染问题；错误提示包含操作类型和文件名，不包含脚本内容。
- [x] 按 UTF-8 正确解码并兼容 UTF-8 BOM，保留原换行和非 ASCII 字符；不得通过
  截断、替换字符或二次错误转码来规避问题。
- [x] 大文件的网络读取和解析放在后台线程；加载期间显示进度，失败后允许重试，
  不能留下空白内容使用户误保存并覆盖原文件。
- [x] 若超过客户端可安全编辑或服务端允许的大小，改为只读预览或显示明确的大小限制，
  不使用笼统的 HTTP 400 作为唯一反馈。
- [ ] 使用包含中文、Emoji、UTF-8 BOM、CRLF/LF、超长单行的 1 MB 和 5 MB 文件分别
  验证打开与保存；内容往返后字节/文本语义一致，界面不假死。
- [x] 长按**脚本文件**时复制当前脚本的规范化完整路径到系统剪贴板，并显示 Android
  Toast“脚本路径已复制”；优先使用服务端返回的 `key`，否则由 `parent + title`
  可靠拼接，不能复制应用下载缓存路径。
- [x] 文件原有的下载、新建和删除操作移到清晰可达的更多菜单；目录长按仍可进入目录
  管理菜单，避免复制路径与破坏性操作冲突。
- [ ] 为路径拼接、剪贴板内容、Toast 触发、长按语义以及大文件成功/失败状态增加测试。

### D. P0：修复依赖安装、重装和删除的响应/状态判定

**当前现象**

- 重新安装依赖时提示：

  ```text
  重新安装失败: Unexpected JSON token at offset 19:
  Expected start of the object, but had '[' instead at path: $.data
  JSON input: {"code":200,"data":[{"id":69,"name":"tesseract-ocr",...}]}
  ```

- 强制删除依赖时出现相同的 `$.data` 数组解析错误。
- 新安装依赖被界面标成“安装失败”，但日志只有类似以下的启动记录，没有成功或失败
  的结束记录：

  ```text
  开始安装依赖 tesseract-ocr，开始时间 2026-08-20 12:43:39
  ```

**已确认的接口行为与初步定位**

- 青龙的 `POST /api/dependencies`、`PUT /api/dependencies/reinstall` 和
  `DELETE /api/dependencies/force` 均可能在 `data` 中返回依赖对象数组。
- 客户端目前只把新增接口声明为 `ApiResponse<List<DependencyInfo>>`；重装与强制删除
  被错误声明为 `ApiResponse<Unit>`。因此 HTTP 和业务码已经成功、服务端任务也可能
  已经开始，但客户端在解析数组时误报失败。
- 青龙安装是异步任务：新增/重装接口成功只表示记录已创建并进入队列，不表示安装
  已完成。“开始安装依赖”也只是启动日志，不能单独作为成功或失败终态。
- 官方状态码为：`0 安装中`、`1 已安装`、`2 安装失败`、`3 删除中`、`4 已删除`、
  `5 删除失败`、`6 队列中`、`7 已取消`。当前卡片把队列中等非终态也使用错误色，
  容易造成“刚提交就失败”的误解。

**目标与验收**

- [x] 重装和强制删除接口按实际响应解析依赖对象数组；同时兼容合法的空 `data`，
  不能再用 `ApiResponse<Unit>` 强制反序列化数组。
- [x] HTTP/业务码成功后显示“任务已提交”或“队列中”，并优先把响应数组中的最新记录
  合并到本地列表；不能因为后续刷新暂时返回旧状态而立即改成失败。
- [ ] 通过依赖日志 WebSocket 和 `GET /api/dependencies/{id}` 跟踪异步状态；WebSocket
  中断时回退为有限频率轮询，离开页面或进入终态后停止监听。
- [x] 只有服务端明确返回状态 `2` 或 `5` 时才显示安装/删除失败；状态 `6` 使用中性
  “队列中”，状态 `0/3` 显示进度，状态 `1/4` 才显示完成。
- [ ] 日志仅有“开始安装”而没有终态时保持“安装中”，刷新日志和记录状态；若服务端
  已标记失败但缺少结束日志，提示“服务端标记失败，日志不完整”，不能伪造成功原因。
- [ ] 新增、重装和删除期间禁用同一依赖的重复操作；批量操作逐项展示已提交、执行中、
  成功、失败和取消数量，解析错误不得覆盖服务端真实执行结果。
- [x] 依赖名称和类型在卡片、确认框与日志标题中用空格或标签明确分隔，避免显示成
  `tesseract-ocrlinux` 这类容易误读的连续文本。
- [ ] 使用返回数组的新增、重装、普通删除和强制删除响应各完成测试；再覆盖排队→安装中
  →成功、排队→安装中→失败、删除失败、取消、WebSocket 断线和日志不完整场景。
- [ ] 在测试青龙实例新增 Linux 依赖 `tesseract-ocr`，确认初始只显示已提交/队列中，
  最终状态严格以青龙返回值和完整结束日志为准。

### F. P2：服务端通知同步到 Android 本地通知（只评估，暂不实现）

**可行性结论**

- 可以实现，但青龙服务端无法可靠地直接向一台普通 Android 手机发送 HTTP 回调。
  手机通常位于 NAT 后方，Android 也会限制后台常驻 HTTP 服务；把 `WEBHOOK_URL`
  指向手机局域网地址只在极少数前台、同网段场景工作，不能作为正式方案。
- 青龙当前没有“通知收件箱/历史列表”API，WorkManager 最短约 15 分钟的轮询既不实时，
  也无法完整补取通知，因此不推荐用客户端轮询伪装实时同步。
- 推荐方案是“青龙自定义 Webhook → 可从公网或指定网络访问的中继服务 → FCM →
  AzureQL 本地通知”。中继可以自托管，但属于新增服务端组件；本功能与
  `qinglong-cloudflare-worker` 无关，也不得复用该项目。

**必须先区分的两类通知**

1. 青龙自身的登录等系统通知使用 `GET/PUT /api/user/notification`，通知配置保存在
   青龙数据库。官方接口当前只保存一种 `type`，切换为 AzureQL Webhook 可能替换用户
   已有的 Telegram、Bark 等系统通知渠道。
2. 定时脚本调用通知脚本时通常读取 `config.sh` 中的 `WEBHOOK_*` 环境变量。这与上面的
   用户通知配置不是同一套数据；只调用 `/api/user/notification` 不会自动改写
   `config.sh`。

**推荐架构（待用户确认）**

- [ ] 设置中提供每个服务器/账户独立的“同步服务端通知”开关；开启时才解释用途并请求
  Android 13+ 的 `POST_NOTIFICATIONS`，拒绝权限不影响其他功能。
- [ ] AzureQL 向中继注册 FCM Token、服务器标识和随机生成的高强度接收凭证；中继只
  接收 HTTPS，不保存青龙登录 Token、密码或脚本环境变量。
- [ ] 青龙 Webhook 使用 `POST application/json`，Body 至少包含 `$title` 和
  `$content`；鉴权密钥放在 Header，不放在通知正文。中继进行限流、长度限制、重复
  消息抑制和凭证撤销。
- [ ] 本地通知按服务器建立 Channel，支持隐藏锁屏正文、点击进入对应账户、单独静音和
  关闭；切换账户或注销时注销相应接收凭证。
- [ ] 若用户已有青龙系统通知渠道，启用前必须提示“官方接口只允许一个渠道”；在没有
  中继转发能力前不得静默覆盖旧配置。

**`config.sh` 注入方案（仅在需要同步脚本通知时启用）**

- 青龙允许通过 `GET /api/configs/detail?path=config.sh` 读取全文，并通过
  `POST /api/configs/save` 保存全文。该接口不是字段级更新，直接覆盖存在并发修改和
  破坏用户自定义内容的风险。
- [ ] 不使用宽泛正则替换整个“自定义通知”章节。客户端只维护带有明确开始/结束标记的
  AzureQL 区块；首次注入前保存原文和内容哈希，显示差异预览并要求用户确认。
- [ ] 保存前重新读取并比较哈希；发现用户或其他程序已修改 `config.sh` 时停止并要求
  合并，不能用旧副本覆盖。
- [ ] Shell 值必须正确转义，`$title`/`$content` 保持为通知脚本运行时占位符。推荐的
  托管区块形态如下，实际地址和凭证必须由已敲定的中继方案生成：

  ```sh
  # >>> AzureQL managed notification >>>
  export WEBHOOK_URL="https://<relay-host>/v1/qinglong/notify"
  export WEBHOOK_BODY='{"title":"$title","content":"$content"}'
  export WEBHOOK_HEADERS=$'Authorization: Bearer <receiver-secret>\nX-AzureQL-Server: <server-id>'
  export WEBHOOK_METHOD="POST"
  export WEBHOOK_CONTENT_TYPE="application/json"
  # <<< AzureQL managed notification <<<
  ```

- `IPPORT='http://qinglong:5700'` 是容器内部访问地址，不是手机或推送中继的回调地址；
  AzureQL 不应自动新增、修改或依赖该变量，除非另一个脚本功能明确需要它。
- [ ] 关闭同步时只删除 AzureQL 自己的托管区块并注销中继凭证，不删除用户手写的
  `WEBHOOK_*` 或其他通知渠道；提供恢复原配置入口。

**实施前必须敲定的决策**

- [ ] 是否接受部署一个可达的自托管中继并使用 FCM；若不接受，只能选择“应用在线时
  接收”或“延迟且不完整的轮询”，不能承诺可靠实时通知。
- [ ] 同步范围是仅青龙系统通知、仅脚本通知，还是两者都要。
- [ ] 若 `/api/user/notification` 已配置其他提供商，是禁止覆盖、让中继同时转发旧渠道，
  还是由用户明确选择替换。
- [ ] 锁屏通知默认显示完整正文、仅标题，还是完全隐藏敏感内容。
- [ ] 中继的部署位置、数据保留期限、凭证轮换与删除策略必须形成单独的威胁模型和验收
  标准后，才能开始 Android 与服务端实现。

### Android 本机运行青龙服务端可行性评估

**结论：标准 Android 12+ 应用中完整内置官方青龙服务端技术上可以尝试，但不适合作为

- [x] 青龙原生部署依赖 Linux 用户空间以及 Node.js、npm、pnpm、Python、pip、Shell、Git、
  定时与进程管理；Docker/Alpine 方案还依赖 `crond`，并非一个可直接放进 APK 的 Java 库。

- [x] Android Virtualization Framework 目前仅覆盖部分 ARM64 设备，创建或管理 pVM 需要平台
  签名权限；不能作为普通 GitHub/应用商店 APK 的通用方案。

- [ ] MCP 设置页默认只显示最近 3 条审计记录，其余记录保持折叠，避免进入页面时形成过长列表。
- [ ] 增加“展开全部/收起”操作；展开后仍最多显示现有上限 20 条，收起后回到最近 3 条。
- [ ] 待确认 Operation 不受审计折叠影响，始终优先显示，避免用户错过批准或拒绝入口。

### 任务标签管理

- [ ] 在任务管理中增加独立的“标签管理”入口，展示标签名称和当前任务引用数。
- [ ] 长按标签弹出“编辑/删除”操作；编辑名称前显示确认提示，并同步更新引用该标签的任务。
- [ ] 仅当引用数为 0 时允许删除标签；仍被任务引用时禁用删除并明确提示引用数量，避免产生
  孤立引用或误删。
- [ ] 标签编辑、删除成功后同步刷新任务列表、筛选条件和编辑弹窗；若当前筛选标签被删除，
  自动清除该筛选条件。

### 从任务命令跳转到脚本

- [ ] 在任务详情/编辑页的命令脚本区域增加“打开脚本”按钮；仅在命令能唯一解析到青龙脚本
  实际路径时显示或启用。
- [ ] 支持常见命令形式及引号、参数，例如 `task foo.py`、`python /ql/scripts/foo.py`、
  `node subdir/foo.js`；不得把参数、管道命令或不明确的多个脚本路径误判为目标脚本。
- [ ] 点击后切换到脚本管理模块，定位真实目录并直接打开当前脚本；脚本不存在、无权限或路径
  已变化时停留在当前页并给出可理解的提示。
- [ ] 为命令解析、路径标准化、跨模块导航和脚本不存在回退补充单元测试与 Compose 导航测试。
